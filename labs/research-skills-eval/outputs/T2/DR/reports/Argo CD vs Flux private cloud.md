# Flux wins the air gap, Argo wins the UI

For an air-gapped, multi-tenant private cloud with 40 Kubernetes clusters, LDAP/AD SSO and on-prem GitLab, **Flux (run per cluster and managed through the Flux Operator) is the better fit as the delivery engine in late 2026**. **Argo CD is the better fit only if a shared, SSO-backed self-service UI for tenant developers is the top requirement.** Flux has the things an air gap needs and Argo CD does not: an official air-gapped install procedure, a first-party `flux mirror` tool, deploy-time Cosign/Notation verification of mirrored OCI artifacts, and a pull model that keeps credentials for all 40 clusters out of any single hub. It also isolates tenants through Kubernetes impersonation, a mature model, where Argo CD's equivalent was still beta in v3.5/3.6. On GitLab, Flux bootstraps directly against self-managed instances and posts commit statuses and MR comments natively, and GitLab's own docs describe Flux as its GitOps engine. Argo CD's real advantage is the user layer: a mature web UI, bundled Dex that federates AD over LDAPS, Casbin RBAC that maps AD groups to per-project roles, and an application-level audit trail. Flux pushes all of that down to Kubernetes RBAC and an AGPL-licensed UI from a single vendor. The choice therefore comes down to where you want the security boundary and who your users are. Platform teams that are comfortable with Kubernetes-native RBAC should choose Flux. Organisations whose tenants are application developers without `kubectl` access will find Argo CD's UI worth the extra air-gap and isolation work.

## Flux ships an air-gap playbook; Argo CD leaves you to build one

The gap between the two projects is widest in air-gapped installation, and this is the constraint the environment cannot relax. Flux has an **official air-gapped installation page**. You list images with `flux install --export`, copy the six `ghcr.io/fluxcd/*` controllers to an internal registry with `crane`, and bootstrap with `--registry=registry.internal/fluxcd` against an internal Git URL. Registry credentials are wired into the controller pods automatically ([Flux air-gapped](https://fluxcd.io/flux/installation/configuration/air-gapped/)). Since August 2026 there is also the official **`flux mirror` plugin**. It declaratively syncs container images, OCI Helm charts and Flux OCI artifacts into the internal registry "so clusters don't contact upstream registries during reconciliation." It republishes HTTP Helm repositories as OCI and can optionally carry OCI 1.1 referrers (signatures, SBOMs, attestations) across the gap ([flux-mirror plugin](https://fluxcd.io/flux/cli-plugins/flux-mirror/); [Flux blog 2026](https://v2-9.docs.fluxcd.io/blog/)). The Flux Operator goes further. When `distribution.artifact` is left unset, it uses manifests embedded in its own image, which its docs call "the recommended setting for air-gapped environments." A semver range such as `"2.8.x"` in `distribution.version` makes upgrades a matter of mirroring a new operator image ([FluxInstance CRD](https://fluxoperator.dev/docs/crd/fluxinstance/)).

Argo CD's installation docs **do not mention air-gapped, offline or private-registry installs**. The manifests are referenced from GitHub URLs, and the Helm chart is described as "currently community maintained" ([Argo CD installation](https://argo-cd.readthedocs.io/en/stable/operator-manual/installation/)). Operators build the mirror list themselves from three registries: `quay.io/argoproj/argocd`, Dex from `ghcr.io/dexidp/dex`, and Redis (plus HAProxy for HA) from a public AWS ECR mirror. They then rewrite every reference through Helm values or Kustomize ([argo-helm values.yaml](https://raw.githubusercontent.com/argoproj/argo-helm/main/charts/argo-cd/values.yaml)). They also have to replace the default SSH known hosts, which cover only public SaaS Git hosts, with their internal GitLab's keys ([Argo CD declarative setup](https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/)). None of this is hard, and it is a one-time cost. The cost recurs, though, because Argo CD ships a minor every quarter and patches only the three latest ([Argo CD release cadence](https://argo-cd.readthedocs.io/en/stable/developer-guide/release-process-and-cadence/)). Every upgrade means vendoring manifests and re-mirroring by hand. One caveat cuts the other way: downstream distributions such as OpenShift GitOps may document air-gapped Argo CD, and those were not examined.

Supply-chain verification tips this further toward Flux. Flux verifies **Git commits and tags (PGP and SSH)**, and verifies **OCI artifacts with Cosign (key-based or keyless) or Notation**. For OCIRepository it supports a self-hosted Sigstore trust root (`trustedRootSecretRef`) ([Flux GitRepository](https://fluxcd.io/flux/components/source/gitrepositories/); [Flux OCIRepository](https://fluxcd.io/flux/components/source/ocirepositories/)). Argo CD 3.5 replaced its deprecated GPG feature with an AppProject `sourceIntegrity` framework. Its docs state plainly that "verification is supported only for Git repositories. It is not possible with Helm or OCI application sources" ([Argo CD source integrity git gpg](https://argo-cd.readthedocs.io/en/stable/user-guide/source-integrity-git-gpg/)). In an air gap, artifacts are usually mirrored as OCI precisely so that signatures can travel with them. That makes Argo CD's Git-only check a material gap, and closing it means adding an admission controller such as Kyverno. Two caveats apply to Flux. Keyless Cosign defaults to the public Fulcio and Rekor services, so air-gapped sites should use Cosign keys, Notation, or a self-hosted Sigstore. And the HelmChart page still calls keyless verification "experimental", with no custom-root support ([Flux HelmChart](https://fluxcd.io/flux/components/source/helmcharts/)). Both projects sign their own release images with Cosign and publish SLSA L3 provenance and SBOMs ([Flux security](https://fluxcd.io/flux/security/); [Argo CD signed release assets](https://argo-cd.readthedocs.io/en/stable/operator-manual/signed-release-assets/)).

## Forty clusters favour pull over a credential-holding hub

Topology sets the security posture of the whole fleet. Classic Argo CD is hub-and-spoke push. The central instance holds a cluster Secret for every spoke in its own namespace and needs network reach to each spoke's API server ([Argo CD Projects](https://argo-cd.readthedocs.io/en/stable/user-guide/projects/)). At 40 clusters, that namespace holds what are usually cluster-admin credentials for the entire private cloud, which makes it the most valuable target in the estate. The central instance also has to be sharded. The stable `legacy` sharding algorithm spreads clusters unevenly, and the better `round-robin` and `consistent-hashing` methods are still listed under **"Alpha Features"** ([Argo CD HA](https://argo-cd.readthedocs.io/en/stable/operator-manual/high_availability/)). The repo-server and Redis then become shared bottlenecks across all tenants. Neither project publishes a tested cluster ceiling, so the scaling risk at 40 is not known precisely. It is a matter of operational tuning, not a hard limit.

The Argo project's answer is **argocd-agent**. Agents on each workload cluster dial out to a central principal, so "the control plane does not need to store credentials for workload clusters," and reconciliation runs locally ([argocd-agent architecture](https://argocd-agent.readthedocs.io/latest/concepts/architecture/)). It is moving quickly: hybrid push-to-pull migration in v0.9, SPIFFE/SPIRE and certificate blocklists in v0.10, and hot TLS reload in v0.11 on November 11, 2026 ([argocd-agent releases](https://github.com/argoproj-labs/argocd-agent/releases)). Red Hat ships it in OpenShift GitOps 1.19 ([Red Hat OpenShift GitOps 1.19](https://docs.redhat.com/en/documentation/red_hat_openshift_gitops/1.19/html-single/argo_cd_agent_installation)). Upstream, however, it is still a **pre-1.0 argoproj-labs project**. Its docs say they "may be incomplete or outdated", and its principal HA is labelled beta ([argocd-agent docs](https://argocd-agent.readthedocs.io/latest/)). Standardising 40 production clusters on it now means betting on incubation-level software, unless you buy Red Hat's supported build.

Flux is pull-based per cluster by default, so each cluster's load stays local. Its own sharding guidance applies only at "tens of thousands of applications" ([Flux sharding](https://fluxcd.io/flux/installation/configuration/sharding/)), so 40 clusters do not change any single installation's scaling profile. The cost moves to fleet lifecycle: you run 40 installations, not one. The Flux Operator's FluxInstance and ResourceSet CRDs exist to template exactly that ([ResourceSet CRD](https://fluxoperator.dev/docs/crd/resourceset/)). ControlPlane's **D2 "Gitless GitOps" reference architecture** fits an air gap closely. CI turns Git into signed OCI artifacts, and production clusters "never contact the Git server directly," so the internal registry becomes the single verifiable distribution point ([ControlPlane D2](https://fluxcd.control-plane.io/guides/d2-architecture-reference/)). Flux can also run hub-and-spoke through `.spec.kubeConfig` ([Flux Kustomization API](https://fluxcd.io/flux/components/kustomize/kustomizations/)). On-prem, though, that brings back centrally stored kubeconfigs, which defeats the point.

## Tenant isolation is native in Flux and still beta in Argo CD

The two tools draw the tenant boundary in different places. Argo CD enforces isolation in its own API server and controller. AppProjects restrict source repos, destinations and resource kinds, and project roles map to OIDC groups ([Argo CD Projects](https://argo-cd.readthedocs.io/en/stable/user-guide/projects/)). The docs themselves concede, however, that "by default, application syncs in Argo CD have the same privileges as the Argo CD control plane." The fix is per-project sync impersonation through `destinationServiceAccounts`. It arrived only in **v3.5.0 and is labelled "beta-quality"** ([Argo CD sync impersonation](https://argo-cd.readthedocs.io/en/stable/operator-manual/app-sync-using-impersonation/)). Getting strict isolation in Argo CD means combining several things: apps in any namespace, `sourceNamespaces`, project-scoped clusters, and beta impersonation with enforcement on. The docs also carry sharp warnings, such as never placing user-controlled namespaces in privileged projects ([Apps in any namespace](https://argo-cd.readthedocs.io/en/stable/operator-manual/app-any-namespace/)).

Flux has never had a separate privilege layer to bolt isolation onto. Its controllers impersonate the ServiceAccount named on each tenant's Kustomization or HelmRelease, and the security page states that "Flux does not reconcile a tenant's repo under the `cluster-admin` role." Three lockdown flags make this mandatory, and none carries an experimental label: `--no-cross-namespace-refs`, `--no-remote-bases` and `--default-service-account` ([Flux security](https://fluxcd.io/flux/security/); [Flux multi-tenancy lockdown](https://fluxcd.io/flux/installation/configuration/multitenancy/)). The catch is that this is opt-in at bootstrap. By default the controllers run as cluster-admin, so a platform team that skips the lockdown patches gets no isolation at all. Flux 2.10 (October 2026) made object-level workload identity GA and added SPIFFE mTLS between controllers ([flux2 releases](https://github.com/fluxcd/flux2/releases)). Its isolation is enforced by the Kubernetes API server itself, which is least privilege by design. That matters more in a regulated private cloud than whether a UI is available.

## AD SSO is Argo CD's strongest argument, and the main cost of Flux

This is where Argo CD clearly leads. Its bundled Dex federates Active Directory through the LDAP connector. It supports nested groups through `recursionGroupAttr`, and the Dex docs strongly recommend LDAPS on port 636 ([Dex LDAP connector](https://dexidp.io/docs/connectors/ldap/)). Argo CD can also point straight at Keycloak or ADFS over OIDC ([Argo CD User Management](https://argo-cd.readthedocs.io/en/stable/operator-manual/user-management/)). AD group names map to roles through Casbin `g,` lines and AppProject roles, with `deny` overriding `allow`. Fine-grained sub-resource rules arrived in v3.0, and `argocd admin settings rbac can` lets you test policy ([Argo CD RBAC](https://argo-cd.readthedocs.io/en/stable/operator-manual/rbac/)). Tenants can view logs and open a shell through the UI without holding any Kubernetes RBAC. Argo CD also emits Kubernetes events that record the actor and logs API requests, which gives an application-level audit trail ([Argo CD Security](https://argo-cd.readthedocs.io/en/stable/operator-manual/security/)). The Dex setup has known weaknesses. It is **unsafe to run with more than one replica without a persistent storage backend**. Group changes take effect only after the user logs in again. And Dex sessions cannot be refreshed silently, so users re-authenticate every 24 hours ([Argo CD User Management](https://argo-cd.readthedocs.io/en/stable/operator-manual/user-management/)).

Core Flux has no UI and no login; Kubernetes RBAC is its only boundary ([Flux Ecosystem](https://fluxcd.io/ecosystem/)). For CLI users, that means AD groups have to reach the kube-apiserver of every one of the 40 clusters through OIDC, via Dex or Keycloak, with RoleBindings carrying the policy. The realistic UI in 2026 is the **Flux Operator Web UI**. It supports OIDC SSO through Dex or Keycloak (with no direct LDAP) and impersonates the logged-in user, so "Kubernetes RBAC is the security boundary for the Web UI" ([Flux Web UI User Management](https://fluxoperator.dev/docs/web-ui/user-management/); [Flux Web UI SSO with Dex](https://fluxoperator.dev/docs/web-ui/sso-dex/)). It is **AGPL-3.0 and built by ControlPlane** ([flux-operator GitHub](https://github.com/controlplaneio-fluxcd/flux-operator)). That calls for legal review if you modify it, and its SSO guide still contradicts itself on admin permissions. Weave GitOps, the former default, has had no stable release since December 2023 and breaks on current HelmRelease APIs ([computingforgeeks](https://computingforgeeks.com/weave-gitops-install-migration-flux/)), so it should not be used. Audit for Flux falls to kube-apiserver audit logs, which record impersonated users. That is standard Kubernetes behaviour, but Flux does not document it. The trade is not one-sided: Argo CD duplicates an authorization layer that has to be kept consistent with Kubernetes RBAC, while Flux reuses the one you already run.

| Requirement | Better fit | Why |
|---|---|---|
| Air-gapped install and upgrades | **Flux** | Official guide, `flux mirror`, operator-embedded distribution |
| Deploy-time signature checks on mirrored OCI/Helm | **Flux** | Cosign/Notation; Argo CD verifies Git GPG only |
| 40-cluster credential exposure | **Flux** (or argocd-agent, pre-1.0) | Pull model; no central cluster-admin Secrets |
| Tenant isolation maturity | **Flux** | Impersonation is core; Argo CD's is beta since 3.5 |
| LDAP/AD SSO and per-tenant UI | **Argo CD** | Bundled Dex, Casbin RBAC, mature shared UI |
| GitLab MR/commit feedback | **Flux** | Native `gitlab` and `gitlabmergerequestcomment` providers |
| GitLab project and MR auto-discovery | **Argo CD** | SCM Provider and Pull Request generators |

## On-prem GitLab splits the decision: Flux for feedback, Argo for discovery

Both tools authenticate to self-managed GitLab with tokens or SSH and handle a private CA. Argo CD keeps CAs in a central hostname-keyed `argocd-tls-certs-cm`, which is easy to manage with an internal PKI. It does have two traps. The ApplicationSet controller needs the CA configured separately. And self-hosted GitLab URLs may need a `.git` suffix, because Argo CD does not follow GitLab's 301 redirect ([Argo CD declarative setup](https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/); [SCM Provider generator](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-SCM-Provider/)). Flux's `flux bootstrap gitlab --hostname` creates the project and registers read-only deploy keys or deploy tokens itself ([Flux bootstrap GitLab](https://fluxcd.io/flux/installation/bootstrap/gitlab/)). Its native `gitlab` provider sets commit status, and since v2.8 its `gitlabmergerequestcomment` provider posts MR comments against self-hosted addresses ([Flux notification providers](https://fluxcd.io/flux/components/notification/providers/); [Flux roadmap](https://fluxcd.io/roadmap)). Image automation, GA since Flux 2.7, can open GitLab MRs through push options ([Flux ImageUpdateAutomation](https://fluxcd.io/flux/components/image/imageupdateautomations/)). GitLab documents Flux on every tier, including Self-Managed, and its agent auto-configures Flux receivers; the page does not mention Argo CD ([GitLab docs](https://docs.gitlab.com/user/clusters/agent/gitops/)). Argo CD has no native GitLab notification service, and the GitLab service page returns a 404. Commit status therefore has to be hand-built from generic webhook templates ([Argo CD webhook service](https://argo-cd.readthedocs.io/en/stable/operator-manual/notifications/services/webhook/)).

Argo CD is far ahead on discovery. Its SCM Provider generator scans GitLab groups and subgroups to produce one Application per project. Its Pull Request generator creates a preview environment per MR. Both take a self-hosted `api` URL and a CA ([SCM Provider](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-SCM-Provider/); [PR generator](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Pull-Request/)). Flux Operator ResourceSet input providers may close part of this gap, but that was not verified.

Both projects are viable long term. Both are CNCF Graduated ([CNCF Flux](https://cncf.io/announcements/2022/11/30/flux-graduates-from-cncf-incubator); [CNCF Argo](https://www.cncf.io/announcements/2022/12/06/the-cloud-native-computing-foundation-announces-argo-has-graduated)), and both are actively released: Argo CD 3.6.2 on November 18 and Flux 2.10.1 on November 20, 2026 ([argo-cd releases](https://github.com/argoproj/argo-cd/releases); [flux2 releases](https://github.com/fluxcd/flux2/releases)). Their risk profiles differ, though. Since Weaveworks shut down, Flux has been sustained mainly by **ControlPlane**, which employs core maintainers and sells hardened images with 24/7 support. Its entry tier is $1,250 per month for one cluster ([ControlPlane](https://control-plane.io/posts/controlplane-backs-the-cncf-flux-project-by-employing-maintainers/); [Pricing](https://fluxcd.control-plane.io/pricing/)). That concentrates the project's sustainability on one vendor, and pricing for 40 clusters is quote-only. Argo CD's commercial ecosystem appears broader, with Red Hat and Octopus among others ([Octopus blog](https://octopus.com/blog/argo-3.3)), but that breadth was not fully sourced.

## Conclusion

The question is less "which tool" than "which layer owns tenancy". In a 40-cluster air gap, the hardest problems are moving signed artifacts across the gap, keeping cluster-admin credentials out of a single hub, and enforcing least privilege on every sync. Flux solves all three natively today. Argo CD reaches parity only through features labelled beta (impersonation), alpha (better sharding) or pre-1.0 (argocd-agent). The Argo roadmap is closing these gaps quickly, so a re-evaluation in 2027, when argocd-agent may reach 1.0 and impersonation may reach GA, could reverse the verdict. Flux's own risks are single-vendor concentration in ControlPlane and an AGPL UI, not technical immaturity.

A pragmatic design for this environment is per-cluster Flux managed by the Flux Operator, D2-style signed OCI artifacts in the internal registry, and AD groups federated through Keycloak or Dex into both the kube-apiservers and the Flux Web UI. Budget explicitly for the work Argo CD would have given you for free: an SSO-backed tenant UI, per-project RBAC policy, and GitLab project auto-discovery. If a pilot shows that tenant developers cannot work without a rich UI, the fallback is Red Hat's supported argocd-agent build, not a classic Argo CD hub that holds credentials for all 40 clusters.
