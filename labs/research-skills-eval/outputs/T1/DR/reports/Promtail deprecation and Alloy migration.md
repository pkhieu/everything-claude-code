# Promtail is dead: migrate to Alloy now

Yes, Grafana Labs deprecated Promtail in favour of Grafana Alloy, and as of November 2026 Promtail is fully end of life. Grafana announced the deprecation with **Loki 3.4 (3.4.0, released 2025-02-12)**. Promtail entered **Long-Term Support on 2025-02-13**, **commercial support ended on 2026-02-28**, and it reached **end of life on 2026-03-02**. Since then it gets no updates of any kind, including security fixes. Grafana has also removed Promtail's source code from the Loki repository, and the Loki 3.7 docs say it is **removed as of Loki 3.7.3**. The official migration path is Grafana's "Migrate from Promtail to Grafana Alloy" guide. It has two steps: convert the config with `alloy convert --source-format=promtail`, then run Alloy with the result. For a temporary transition, Alloy can also load a Promtail config directly with `alloy run --config.format=promtail`. Conversion usually works but is not perfect. The converter is labelled public preview. It cannot convert Promtail's WAL, stdin targets, CLI flags or environment variables. Positions files, metrics, dashboards and Kubernetes discovery need hand checks before you go to production. One exception matters: **lambda-promtail is explicitly excluded** from the deprecation.

## Loki 3.4 deprecated Promtail in February 2025, not Loki 3.0

The Loki 3.4 release notes say Promtail "is deprecated, as the code has been merged into Grafana Alloy", and that "this deprecation does NOT include the lambda-promtail client" ([Loki v3.4 release notes](https://grafana.com/docs/loki/latest/release-notes/v3-4/)). The official announcement followed on 2025-02-14 in a blog post titled "Grafana Loki 3.4: standardized storage config, sizing guidance, and Promtail merging into Alloy". It described the move as "deprecating Promtail and fully merging its capabilities into Alloy" ([Grafana Labs blog](https://grafana.com/blog/grafana-loki-3-4-standardized-storage-config-sizing-guidance-and-promtail-merging-into-alloy)). The same release notes recorded the parallel deprecation of Grafana Agent, which reached EOL on November 1, 2025. Alloy replaces both collectors ([Loki v3.4 release notes](https://grafana.com/docs/loki/latest/release-notes/v3-4/)).

One official source disagrees. The Loki 3.7 release notes say "Promtail was deprecated in Loki 3.0" ([Loki v3.7 release notes](https://grafana.com/docs/loki/latest/release-notes/v3-7/)). The Loki 3.0 notes, however, mention Promtail only in bug fixes, with no deprecation or feature freeze ([Loki v3.0 release notes](https://grafana.com/docs/loki/latest/release-notes/v3-0/)). The 3.4 release notes, the 3.4 blog post and the LTS banner all agree on Loki 3.4 in February 2025. The "3.0" wording is best read as an editorial error, so treat **Loki 3.4 as the formal deprecation point**.

## Three dates defined the wind-down, and Grafana met all of them

Grafana published the timeline in February 2025 as a forecast. The Promtail docs banner said Promtail "will no longer receive any new feature updates, but it will receive critical bug fixes and security fixes". It added that commercial support would end after an LTS phase lasting "about 12 months until February 28, 2026", and that Promtail was "expected to reach EOL on March 2, 2026, afterwards no future support or updates will be provided" ([GEL v3.5.x Promtail docs](https://grafana.com/docs/enterprise-logs/v3.5.x/send-data/promtail/)). The current documentation states these dates as fact: "Promtail is end of life (EOL) as of March 2, 2026" and "Commercial support has ended" ([Loki Promtail docs](https://grafana.com/docs/loki/latest/send-data/promtail/)). The Alloy guide agrees, saying Promtail "is no longer maintained" ([Alloy: Migrate from Promtail](https://grafana.com/docs/alloy/latest/set-up/migrate/from-promtail/)). There was no extension.

| Phase | Date | What it meant |
|---|---|---|
| Deprecation announced | Loki 3.4.0, 2025-02-12 (blog 2025-02-14) | Alloy named as the successor |
| LTS begins | 2025-02-13 | No new features; critical bug and security fixes only |
| Commercial support ends | 2026-02-28 | End of paid Grafana support for Promtail |
| End of life | 2026-03-02 | No support, fixes or releases of any kind |
| Code removed | Loki 3.7.3 (backport merged 2026-03-25; release 2026-06-24) | Promtail no longer built or shipped by Loki |

The LTS and EOL dates apply to Promtail as a project. Both the OSS Loki docs and the Grafana Enterprise Logs docs carry them. The only date that separates commercial from OSS users is the end of commercial support on 2026-02-28. Grafana published no other OSS-versus-commercial split.

Removal followed soon after EOL. In PR #21248, which backports #21245 to the 3.7 line and was merged 2026-03-25, the maintainer wrote: "Promtail reached EOL on March 2, so in this PR I'm removing its source code from this repo." The PR also said that "Promtail binaries shouldn't be available anymore". Some Promtail API code stays in the repo because clients such as Fluent Bit depend on it ([grafana/loki PR #21248](https://github.com/grafana/loki/pull/21248)). The v3.7.3 changelog lists the removal under Features ([Loki v3.7.3 release](https://github.com/grafana/loki/releases/tag/v3.7.3)). The current release lines are v3.7.10 stable and the v4.0.0 release candidates ([grafana/loki releases](https://github.com/grafana/loki/releases)). Promtail's directory is gone from `clients/cmd` on main ([grafana/loki clients/cmd](https://github.com/grafana/loki/tree/main/clients/cmd)). Three points are still unclear: which release was the last to ship Promtail artifacts, whether the still-patched 3.6.x line builds Promtail, and what happens to the old `grafana/promtail` images and the standalone Helm chart. Older binaries will keep running against Loki for now, but any CVE found in them will stay unpatched. Grafana's instruction is: "If you are currently using Promtail, you must migrate to Alloy or another supported client" ([Loki Promtail docs](https://grafana.com/docs/loki/latest/send-data/promtail/)).

## The official path is to convert the config, review it, then run Alloy

The official guide is "Migrate from Promtail to Grafana Alloy" in the Alloy docs ([Alloy migrate guide](https://grafana.com/docs/alloy/latest/set-up/migrate/from-promtail/)). It is also linked from the Loki "Migrate to Alloy" index, next to the guides for Grafana Agent, the OpenTelemetry Collector and Prometheus ([Loki migrate-to-alloy](https://grafana.com/docs/loki/latest/setup/migrate/migrate-to-alloy/)). The first step converts the config:

```shell
alloy convert --source-format=promtail --output=<OUTPUT_CONFIG_PATH> <INPUT_CONFIG_PATH>
```

The second step runs Alloy with the generated file. Two flags help with debugging. `--report` writes a diagnostic report. `--bypass-errors` forces a best-effort conversion, which the guide warns "may not match the original Promtail configuration" and should be tested before production ([Alloy migrate guide](https://grafana.com/docs/alloy/latest/set-up/migrate/from-promtail/)). The converter targets **Promtail v2.8.x** syntax. Grafana says "nearly all Promtail features are supported", and the converter flags anything else as an Error or a Warning. The command is marked **public preview**, so it requires the `stability.level` flag to be set to `public-preview` or lower ([convert CLI reference](https://grafana.com/docs/alloy/latest/reference/cli/convert/)). Converted values that equal Alloy's defaults are left out of the output, so a short output file does not mean settings were lost.

The second official option skips the saved file. `alloy run --config.format=promtail <INPUT_CONFIG_PATH>` converts the config in memory at startup and does not save the result ([Alloy migrate guide](https://grafana.com/docs/alloy/latest/set-up/migrate/from-promtail/)). This option is also public preview. The run reference warns that bypassing conversion errors means "the resulting conversion may not be equivalent to the original configuration" ([run.md](https://github.com/grafana/alloy/blob/main/docs/sources/reference/cli/run.md)). The migration guide is blunter about `--config.bypass-conversion-errors`: "Don't use this flag in a production environment" ([Alloy migrate guide](https://grafana.com/docs/alloy/latest/set-up/migrate/from-promtail/)). Use this option to keep logs flowing during a transition, not as the end state. Commit a converted, reviewed `.alloy` file instead.

The converter turns each Promtail `scrape_config` into a pipeline of Alloy components. Service discovery becomes `discovery.*` components, `relabel_configs` becomes `discovery.relabel`, and file tailing becomes `loki.source.file`. Push-style receivers (journal, syslog, push API, Kafka, GCP, Windows events, Cloudflare, GELF, Heroku, Azure Event Hubs) become `loki.source.*` components with `loki.relabel`. `pipeline_stages` becomes `loki.process`, and each `clients` entry becomes its own `loki.write` ([promtailconvert.go](https://github.com/grafana/alloy/blob/main/internal/converter/internal/promtailconvert/promtailconvert.go)). The guide works through a systemd example in which `journal` becomes `loki.relabel` plus `loki.source.journal`. In that example the `alloy` user must belong to the `adm` and `systemd-journal` groups ([Alloy migrate guide](https://grafana.com/docs/alloy/latest/set-up/migrate/from-promtail/)).

## Conversion gaps sit in WAL, metrics, positions and DaemonSet assumptions

The converter source shows which Promtail features are not migrated automatically. Several block conversion with an Error: an enabled WAL ("Promtail's WAL is currently not supported in Alloy"), stdin targets, `server.http_path_prefix`, and any pipeline stage the converter does not recognise. Other settings only raise a Warning. Tracing is not migrated. A non-`info` log level, `profiling_enabled`, and a disabled health-check target are dropped. Changes in meta-monitoring metrics mean you must rewrite alerts and dashboards that watch Promtail's own metrics ([validate.go](https://github.com/grafana/alloy/blob/main/internal/converter/internal/promtailconvert/validate.go); [stages.go](https://github.com/grafana/alloy/blob/main/internal/converter/internal/promtailconvert/internal/build/stages.go)). One change in behaviour is easy to miss. Promtail's global `limits_config` readline rate limit becomes a `stage.limit` in every `loki.process`, and those limits "apply independently per pipeline rather than across all pipelines combined". A fleet-wide throttle can therefore end up looser than before ([validate.go](https://github.com/grafana/alloy/blob/main/internal/converter/internal/promtailconvert/validate.go)). The guide adds that CLI-only flags such as `-max-line-size` and environment variables are not converted. It also notes that the converter assumes Kubernetes pod discovery runs as a DaemonSet, so other deployment shapes must edit the generated `discovery.kubernetes` block ([Alloy migrate guide](https://grafana.com/docs/alloy/latest/set-up/migrate/from-promtail/)).

The guide spends little time on read offsets. It says only that "the positions file is saved at a different location" and that setups such as Kubernetes Persistent Volumes may need updating ([Alloy migrate guide](https://grafana.com/docs/alloy/latest/set-up/migrate/from-promtail/)). The converter source fills the gap. Every generated `loki.source.file` gets `legacy_positions_file` set to Promtail's positions path, which defaults to `/var/log/positions.yaml` ([scrape_builder.go](https://github.com/grafana/alloy/blob/main/internal/converter/internal/promtailconvert/internal/build/scrape_builder.go); [positions.go](https://github.com/grafana/alloy/blob/main/internal/loki/promtail/positions/positions.go)). Alloy imports those offsets once, and only "if the new positions file doesn't exist and the `legacy_positions_file` is valid". It matches entries by path and labels, then by path alone ([loki.source.file reference](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.file/)). For a clean handover, follow this order. Stop Promtail. Make its positions file readable at the same path inside Alloy. Start Alloy with a fresh storage path. Then persist that storage path. The last step matters because the converter sets `on_positions_file_error` to `restart_from_beginning`, which can duplicate logs. The Alloy Helm chart's default `storagePath` of `/tmp/alloy` carries the warning that "data is lost between reboots" ([values.yaml](https://github.com/grafana/alloy/blob/main/operations/helm/charts/alloy/values.yaml)). Journal offsets need more work. The converter does not set `legacy_position` for journal sources ([journal.go](https://github.com/grafana/alloy/blob/main/internal/converter/internal/promtailconvert/internal/build/journal.go)), so you must add that block to `loki.source.journal` by hand. Users have also asked Grafana to document this behaviour ([community.grafana.com](https://community.grafana.com/t/clarify-loki-source-journal-legacy-position-behavior-when-migrating-from-promtail-to-alloy-avoid-duplicate-logs/163400)).

On Kubernetes, the official route is the `grafana/alloy` Helm chart from `grafana.github.io/helm-charts` ([Alloy on Kubernetes](https://grafana.com/docs/alloy/latest/set-up/install/kubernetes/)). It deploys a DaemonSet by default, but `alloy.mounts.varlog` defaults to `false`. A Promtail-style setup that tails files must turn that on and give the chart a persistent `storagePath` ([values.yaml](https://github.com/grafana/alloy/blob/main/operations/helm/charts/alloy/values.yaml)). Grafana has not published a Helm-specific guide for moving from the Promtail chart to the Alloy chart, or an official runbook for running both side by side. Running Promtail and Alloy against the same files at once will duplicate logs. The safer pattern is a short stop-and-start cutover that relies on the legacy positions import.

## Conclusion

The question is no longer whether to migrate but how much risk you carry by waiting. Promtail has been unmaintained for almost nine months and no longer exists in the Loki source tree, so every remaining deployment is unpatched software. The tooling makes this a modest project rather than a rewrite. The hard parts are around the config translation: offsets, self-monitoring and rate-limit behaviour, which the official guide mentions only briefly and the converter source explains in detail.

Teams should also note a quiet inconsistency in Grafana's guidance. The tool Grafana recommends for leaving an EOL product is still labelled public preview. Grafana documents the main offset-preservation mechanism for Grafana Agent rather than for Promtail. Journal offsets are left for you to handle by hand. Treat the converter output as a first draft, test it on one node with its positions file mounted, and remember that lambda-promtail users do not need to migrate at all.
