# Nine severe CVEs outlast ingress-nginx's retirement

From January 2025 to 24 November 2026, the Kubernetes community ingress-nginx controller received **nine Critical or High CVEs**, and every one leads to the same outcome: code execution inside the controller and theft of the Secrets it can read, which in a default install means **all Secrets in the cluster**. The March 2025 "IngressNightmare" batch brought the only Critical, **CVE-2025-1974 (CVSS 9.8)**, along with three High annotation-injection bugs. All four are fixed in **controller v1.11.5 / v1.12.1 (Helm charts 4.11.5 / 4.12.1)**. Five more High (8.8) injection CVEs were disclosed in February and March 2026. The cumulative fix floor for them is **controller v1.13.9, v1.14.5 or v1.15.1 (charts 4.13.9 / 4.14.5 / 4.15.1)**, released 19 March 2026. Those were the project's last releases: the repository was archived on 24 March 2026, and a vulnerability disclosed in November 2026 was explicitly marked won't-fix. Clusters that cannot upgrade have mitigations that cover most, but not all, of these CVEs: turn off the validating admission webhook or restrict network access to it; lower `annotations-risk-level` and disable snippet annotations; and enforce an API-server-side admission policy that rejects specific annotations and the `ImplementationSpecific` pathType. No documented workaround exists for CVE-2025-1097, CVE-2025-1098, CVE-2025-15566 or CVE-2026-4342, so upgrading to v1.15.1 and then migrating off is the only complete answer.

## One Critical and three High CVEs made up March 2025's IngressNightmare

The Kubernetes Official CVE Feed lists only one ingress-nginx disclosure event in calendar 2025: five CVEs published together on 23–24 March 2025 and found by Wiz Research, which named the batch "IngressNightmare" ([Kubernetes CVE feed](https://kubernetes.io/docs/reference/issues-security/official-cve-feed/index.json); [Wiz](https://www.wiz.io/blog/ingress-nginx-kubernetes-vulnerabilities)). The centrepiece, **CVE-2025-1974**, lets "an unauthenticated attacker with access to the pod network" run arbitrary code as the controller through its Validating Admission Controller ([kubernetes/kubernetes#131009](https://github.com/kubernetes/kubernetes/issues/131009)). On its own, the webhook bug is an injection point. Chained with the annotation bugs, the Kubernetes blog says it gives "a good chance of taking over your Kubernetes cluster, with no credentials or administrative access required". The blog also says ingress-nginx runs in **over 40% of Kubernetes clusters** and that the pod network is often reachable from the whole cloud VPC or corporate network ([Kubernetes blog](https://kubernetes.io/blog/2025/03/24/ingress-nginx-cve-2025-1974/)). At disclosure, Wiz counted **more than 6,500 clusters** exposing a vulnerable admission controller to the public internet ([Wiz](https://www.wiz.io/blog/ingress-nginx-kubernetes-vulnerabilities)).

| CVE | Severity | Vector | Fixed controller (chart) |
|---|---|---|---|
| CVE-2025-1974 | **Critical 9.8** (PR:N) | Unauthenticated RCE via the admission webhook | v1.11.5 / v1.12.1 (4.11.5 / 4.12.1) |
| CVE-2025-1097 | High 8.8 | `auth-tls-match-cn` annotation injection | same |
| CVE-2025-1098 | High 8.8 | `mirror-target` / `mirror-host` annotation injection | same |
| CVE-2025-24514 | High 8.8 | `auth-url` annotation injection | same |
| CVE-2025-24513 | Medium 4.8 (context) | Admission-controller path traversal, used as a chaining primitive | same |

All five share the affected range (everything before v1.11.5, plus v1.12.0) and were patched in one coordinated release ([CVE feed](https://kubernetes.io/docs/reference/issues-security/official-cve-feed/index.json); [Artifact Hub 4.12.1](https://artifacthub.io/packages/helm/ingress-nginx/ingress-nginx/4.12.1); [Artifact Hub 4.11.5](https://artifacthub.io/packages/helm/ingress-nginx/ingress-nginx/4.11.5)). The fix for CVE-2025-1974 removed NGINX configuration testing from the admission path entirely, which closed the remote route to the injection bugs ([Wiz](https://www.wiz.io/blog/ingress-nginx-kubernetes-vulnerabilities)). Public proof-of-concept exploits appeared within about five days ([GBHackers](https://gbhackers.com/poc-exploit-released-ingress-nginx-rce)). However, **none of these CVEs is in CISA's KEV catalog** as of the 23 November 2026 version, and the official advisory reports no known indicators of compromise ([CISA KEV](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json); [#131009](https://github.com/kubernetes/kubernetes/issues/131009)). The fair label is "weaponized, not confirmed exploited". Absence from KEV is weak reassurance, though, for a bug class this easy to reach.

## Five more High injection bugs in 2026 set the final floor at v1.15.1

The 2026 disclosures contain no Critical-rated CVE, but five High (CVSS 8.8, PR:L) bugs, each of the same kind: an authenticated user who can create or edit an Ingress injects nginx configuration, gets RCE in the controller, and reads Secrets ([NVD CVE-2026-24512](https://nvd.nist.gov/vuln/detail/CVE-2026-24512); [NVD CVE-2026-4342](https://nvd.nist.gov/vuln/detail/CVE-2026-4342)). Each wave raised the minimum safe version, so only the last release line clears all of them.

| CVE | Injection point | Disclosed | Fixed controller (chart) |
|---|---|---|---|
| CVE-2026-24512 | `rules.http.paths.path` field | 2 Feb 2026 | v1.13.7 / v1.14.3 (4.13.7 / 4.14.3) ([#136678](https://github.com/kubernetes/kubernetes/issues/136678)) |
| CVE-2026-1580 | `auth-method` annotation | 2 Feb 2026 | v1.13.7 / v1.14.3 ([#136677](https://github.com/kubernetes/kubernetes/issues/136677)) |
| CVE-2025-15566 | `auth-proxy-set-headers` annotation | 6 Feb 2026 | v1.12.5 / v1.13.1 ([#136789](https://github.com/kubernetes/kubernetes/issues/136789)) |
| CVE-2026-3288 | `rewrite-target` annotation | 9 Mar 2026 | v1.13.8 / v1.14.4 / v1.15.0 (4.13.8 / 4.14.4 / 4.15.0) ([#137560](https://github.com/kubernetes/kubernetes/issues/137560)) |
| CVE-2026-4342 | "Comment-based" injection via a combination of annotations | 19 Mar 2026 | **v1.13.9 / v1.14.5 / v1.15.1 (4.13.9 / 4.14.5 / 4.15.1)** ([#137893](https://github.com/kubernetes/kubernetes/issues/137893)) |

Chart-to-controller mappings come from the project's release PRs ([PR #14512](https://github.com/kubernetes/ingress-nginx/pull/14512); [PR #14673](https://github.com/kubernetes/ingress-nginx/pull/14673); [PR #14738](https://github.com/kubernetes/ingress-nginx/pull/14738)). Three details trip up inventories. First, **CVE-2025-15566 carries a 2025 ID but was disclosed on 6 February 2026**, and its fixed builds had shipped quietly on 12 August 2025. Its charts are 4.12.5 and 4.13.1 on Artifact Hub, although the advisory does not name them ([Artifact Hub 4.13.1](https://artifacthub.io/packages/helm/ingress-nginx/ingress-nginx/4.13.1)). Second, the CVE-2026-4342 advisory labels its 8.8 score "Medium", but NVD and the CNA metric both rate it **High** ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-4342)). Third, vendor research describes CVE-2026-3288 as an incomplete fix for CVE-2026-24512, so a February 2026 patch does not cover the path/rewrite class ([Sysdig](https://www.sysdig.com/blog/detecting-cve-2026-3288-cve-2026-24512-ingress-nginx-configuration-injection-vulnerabilities-for-kubernetes)). The same February wave also fixed two lower-severity bugs, the admission-webhook memory DoS CVE-2026-24514 (6.5) and the auth-url bypass CVE-2026-24513 (3.1) ([#136680](https://github.com/kubernetes/kubernetes/issues/136680); [#136679](https://github.com/kubernetes/kubernetes/issues/136679)).

## Retirement turned every later bug into a permanent exposure

SIG Network and the Security Response Committee announced on 11 November 2025 that best-effort maintenance would end in March 2026, after which there would be "no further releases, no bugfixes, and no updates to resolve any security vulnerabilities". They recommended migrating to Gateway API or another Ingress controller "immediately" ([Kubernetes blog](https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/)). Among the reasons, the post singles out the snippet annotations: "Yesterday's flexibility has become today's insurmountable technical debt". The 2026 CVEs bear this out, as each is another annotation or field that reaches the nginx config. **Controller v1.15.1 / chart 4.15.1, released 19 March 2026, is the final upstream release.** The repository went read-only on 24 March 2026. Existing images and charts stay downloadable, and running deployments keep working ([GitHub releases](https://github.com/kubernetes/ingress-nginx/releases); [README](https://github.com/kubernetes/ingress-nginx/blob/main/README.md)).

The consequences arrived quickly. On 5 November 2026 the SRC disclosed a Low (2.7) `mirror-target` data-plane DoS, listed in the feed as "CVE-2026-116472" (an unusual six-digit ID worth confirming). The advisory stated that "Kubernetes will not be issuing a fix for this CVE, because ingress-nginx maintenance ended in March 2026" and pointed to SUSE's fork, version 1.15.2-prime1 ([#143852](https://github.com/kubernetes/kubernetes/issues/143852)). The bundled nginx core is also left behind. NVD lists 2026 nginx flaws scored CVSS 4.0 9.2 / CVSS 3.1 8.1, among them CVE-2026-42945 in the rewrite module ([NVD CVE-2026-42945](https://nvd.nist.gov/vuln/detail/CVE-2026-42945)) and an HTTP/2 use-after-free listed as CVE-2026-123633 ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-123633)). Vendors say these reach ingress-nginx's bundled nginx 1.27.1 and will never be patched upstream ([Aikido](https://www.aikido.dev/blog/nginx2root-critical-nginx-rce-vulnerabilities); [HeroDevs](https://www.herodevs.com/blog-posts/ingress-nginx-cves-nginx-1-31-7-1-30-6)). Those claims come from companies selling patched builds and were not checked against the image build files. They are not ingress-nginx's own CVEs, but they matter to anyone running the image. In practice, "cannot upgrade" now has two meanings: a cluster below v1.15.1 is missing published fixes, and a cluster on v1.15.1 has nothing left to upgrade to. The second group's options are workarounds, a commercial or community fork (SUSE, HeroDevs NES, Aikido's patched image), or migration.

## Layered controls cover most CVEs, with four gaps

The official advisories prescribe mitigations by vulnerability class, and the strongest of them run outside the vulnerable controller. The table below maps each Critical/High CVE to its pre-upgrade mitigation. Entries marked "inferred" combine the project's annotation risk table with the advisories rather than quoting an official workaround.

| CVE | Pre-upgrade mitigation | Source |
|---|---|---|
| CVE-2025-1974 | Disable the validating webhook (`controller.admissionWebhooks.enabled=false`, or delete the `ingress-nginx-admission` ValidatingWebhookConfiguration and remove `--validating-webhook`) | [Kubernetes blog](https://kubernetes.io/blog/2025/03/24/ingress-nginx-cve-2025-1974/) |
| CVE-2025-24514 | Enable `enable-annotation-validation` (default from v1.12.0) | [#131006](https://github.com/kubernetes/kubernetes/issues/131006) |
| CVE-2025-1097, CVE-2025-1098 | No official workaround. Inferred: `annotations-risk-level: Medium` rejects these High-rated annotations | [#131007](https://github.com/kubernetes/kubernetes/issues/131007), [risk table](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/annotations-risk/) |
| CVE-2026-24512 | Admission policy rejecting `pathType: ImplementationSpecific` | [#136678](https://github.com/kubernetes/kubernetes/issues/136678) |
| CVE-2026-1580 | Admission policy rejecting `auth-method` | [#136677](https://github.com/kubernetes/kubernetes/issues/136677) |
| CVE-2026-3288 | Admission policy blocking `rewrite-target` | [#137560](https://github.com/kubernetes/kubernetes/issues/137560) |
| CVE-2025-15566 | No official workaround. Inferred: `annotations-risk-level: Low` or a policy blocking `auth-proxy-set-headers` | [#136789](https://github.com/kubernetes/kubernetes/issues/136789) |
| CVE-2026-4342 | **None published**; upgrade to v1.13.9/v1.14.5/v1.15.1 | [#137893](https://github.com/kubernetes/kubernetes/issues/137893) |

**The webhook is the first decision.** Turning it off removes CVE-2025-1974's entry point and the 2026 webhook DoS, but the blog warns that users lose early warnings about broken Ingress configs, and it asks admins to re-enable the webhook after upgrading ([Kubernetes blog](https://kubernetes.io/blog/2025/03/24/ingress-nginx-cve-2025-1974/)). It also stops admission-time enforcement of the webhook's own checks: `strict-validate-path-type`, which restricts the characters allowed in `Exact`/`Prefix` paths, is validated "on the Admission Webhook" ([ConfigMap docs](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/configmap/)). The alternative Wiz recommends is to keep the webhook but use NetworkPolicy so only the API server can reach it (port 8443 by default), and never expose it publicly ([Wiz](https://www.wiz.io/blog/ingress-nginx-kubernetes-vulnerabilities)). The chart ships with `controller.networkPolicy.enabled: false` and a `failurePolicy: Fail` webhook, so a policy that misidentifies the API server's source address blocks every Ingress create and update ([values.yaml](https://github.com/kubernetes/ingress-nginx/blob/main/charts/ingress-nginx/values.yaml)). Expressing that address is hardest on managed control planes.

**ConfigMap knobs shrink the annotation surface.** `allow-snippet-annotations` already defaults to `false`; keep it that way unless every Ingress author is trusted. `annotations-risk-level` (default `High`) rejects every annotation rated above the configured level ([ConfigMap docs](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/configmap/)). In the current risk table, `mirror-target`, `mirror-host`, `auth-url` and `auth-tls-match-cn` are High, while `rewrite-target` and `auth-proxy-set-headers` are Medium and `auth-method` is Low ([risk table](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/annotations-risk/)). Setting the level to Medium therefore blocks the 2025 annotation vectors, and Low also blocks CVE-2026-3288 and CVE-2025-15566. **No risk level blocks `auth-method`**, which is why CVE-2026-1580 needs an external policy. The CVE-2025-1098 chain also passes payload through the Ingress UID, which annotation regexes never inspect, so the mirror annotations themselves have to be rejected ([Wiz](https://www.wiz.io/blog/ingress-nginx-kubernetes-vulnerabilities)). Older controllers do not necessarily support these knobs, so check them against the running version. Expect breakage: annotation validation has already rejected Ingresses that previously worked ([#13092](https://github.com/kubernetes/ingress-nginx/issues/13092)), and `rewrite-target` is very common.

**API-server admission policy works regardless of the webhook's state.** The 2026 advisories name "a validating admission controller" as the main pre-upgrade defence but do not name an engine. A native ValidatingAdmissionPolicy, or a Kyverno or Gatekeeper rule, runs inside the API server, so it keeps working while the ingress-nginx webhook is disabled. One illustrative and untested design binds with `validationActions: [Deny]` on `networking.k8s.io/v1` Ingress CREATE/UPDATE. It rejects any `nginx.ingress.kubernetes.io/` key among `auth-method`, `rewrite-target`, `mirror-target`, `mirror-host`, `auth-proxy-set-headers` and the snippet annotations, and it rejects any path whose `pathType` is `ImplementationSpecific`. Trusted namespaces get exceptions, and the rollout goes through Audit before Deny. Ready-made library policies are scarce. Kyverno's ingress-nginx ValidatingPolicy ships in Audit mode and enforces a version floor of 1.11.2, which predates every CVE here, so it needs updating before use ([kyverno/policies](https://github.com/kyverno/policies/blob/main/other-vpol/check-ingress-nginx-controller-version-and-annotation-policy/check-ingress-nginx-controller-version-and-annotation-policy.yaml)). Blocking `ImplementationSpecific` breaks regex routing, because the docs require that pathType for regex paths ([ConfigMap docs](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/configmap/)). One limit applies to every engine: CVE-2025-1974 attackers send AdmissionReview requests straight to the controller over the pod network and never pass through the API server. Policy engines do nothing for that path, so it needs the webhook disabled or network-restricted ([Wiz](https://www.wiz.io/blog/ingress-nginx-kubernetes-vulnerabilities)).

## Detection relies on annotation hunting and runtime signals

Every advisory uses `kubectl get pods --all-namespaces --selector app.kubernetes.io/name=ingress-nginx` as the presence check ([Kubernetes blog](https://kubernetes.io/blog/2025/03/24/ingress-nginx-cve-2025-1974/)). From there, compare controller image tags against the floors above. Anything below v1.13.9, v1.14.5 or v1.15.1 is missing published fixes. The advisories' indicators all point to "suspicious data" in the vulnerable annotation or in `rules.http.paths.path`. For the auth-proxy-set-headers bug, the indicator is in the ConfigMap that the annotation references ([#136789](https://github.com/kubernetes/kubernetes/issues/136789)). For the won't-fix mirror bug, it is localhost addresses in `mirror-target` ([#143852](https://github.com/kubernetes/kubernetes/issues/143852)). In practice, hunt current Ingress objects and Kubernetes audit history for braces, semicolons, newlines, `#` comments and directives such as `ssl_engine`, `load_module` or `_by_lua`. That hunting does not catch the Critical webhook attack, because those requests never reach the audit log. Runtime telemetry does: the IngressNightmare chain uploads a shared library through nginx client-body buffering and loads it via `ssl_engine` from `/proc/<pid>/fd/<n>` ([Wiz](https://www.wiz.io/blog/ingress-nginx-kubernetes-vulnerabilities)). Sysdig's Falco rule flags exactly that, an executable `mmap` of a `/proc/*/fd/*` file by an nginx process in a container ([Sysdig](https://www.sysdig.com/blog/detecting-and-mitigating-ingressnightmare-cve-2025-1974)). No vendor detection rules for the 2026 CVEs specifically turned up in this research.

## Conclusion

Ingress-nginx's CVE record from 2025 to 2026 is one design flaw reported many times over. Annotations and path fields that reach the nginx config can be abused, and the Critical webhook bug once let anyone on the pod network abuse them without credentials. The practical lesson is that per-annotation patching was never going to converge. Each fix (24512, then 3288, then 4342) exposed the next injection point within weeks. The most durable mitigations are therefore the ones that remove the attack surface itself rather than match known payloads: API-server admission policy, a low `annotations-risk-level`, and a webhook that pod-network clients cannot reach.

For clusters that cannot upgrade, the realistic sequence is to move to v1.15.1 as soon as change control allows, since it is the only build without known High CVEs. Apply the layered controls during the wait, and treat them as a bridge to a migration date rather than a steady state. CVE-2026-4342 has no workaround, the November 2026 advisory shows that new findings now ship without fixes, and unpatched nginx-core flaws are building up underneath. A cluster still on upstream ingress-nginx in late 2026 has to pick between a vendor fork and a move to Gateway API or another Ingress controller.
